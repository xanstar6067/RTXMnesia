## Особенность западной части хора: перегрузки

В `24_torture_choir_west.hps:94` и :101 есть **две перегрузки ResumeEventTimer**: с одним и двумя аргументами. Обе сохранить с исходными именами. Штатный checker считает уникальные имена и сам не докажет сохранность обеих сигнатур.

Внутренние C#-вызовы могут штатно выбирать перегрузку. На дату плана HplScript.CollectMethods/Invoke хранит первую функцию по имени, а PlayerSimulation использует отражение без выбора перегрузки. Проверить фактические string-callbacks: в исходнике обе ResumeEventTimer вызываются как внутренние helpers, буквальной регистрации имени ResumeEventTimer коллбэком при подготовке плана не найдено. **Не объявлять это блокером по одному предупреждению о повторном имени и не чинить диспетчер заранее.**

Для диагностических call выбрать исходные обработчики с уникальными именами, которые вызывают нужные helpers. Если актуальный код действительно регистрирует перегруженное имя в движке и получает неверную сигнатуру, записать точный сценарий; исправление рантайма/диагностики выполнить отдельно, не переименовывая и не удаляя функцию оригинала.

## Зависимости движка на дату плана

Не считать механику готовой по объявленному имени API:

- AutoSave вызывают все 12 карт; на дату плана это NotPorted.
- Enemy API затрагивают south/north, morgue, sewer, chancel и choir_east. Скрипты/patrol-настройки переносить, ИИ не дописывать.
- ControlRoom использует InteractConnectPropWithRope/MoveObject; Nave — attached props, AttachBodyToStickyArea, InteractConnectPropWithRope и SetNPCAwake; Transept — связи верёвок. Эти вызовы объявлены, но на дату плана не реализованы.
- ChoirWest вызывает PlayPropAnimation; North — SetInsanitySetEnabled. Статус проверять по актуальному коду, включая пустые методы без предупреждения.
- Базовые смерть и возрождение уже перенесены. Не писать «смерть ещё не перенесена», если отсутствует только сброс врагов или конкретная механика CP.

## Правила ручного переноса

Использовать using RTXMnesia.ScriptApi, базовый HplScript, namespace и атрибут из раздела этой части. Образцы: RainyHall.cs, OldArchives.cs, EntranceHall.cs, затем порты 03–14 и их журналы.

1. Переносить вручную, функция за функцией, в исходном порядке, с теми же именами, параметрами, переменными, строками, числами, английскими комментариями и порядком операций. Не переписывать «по смыслу», не объединять похожие события и не пропускать неиспользуемый/отладочный/недостижимый код.
2. Только существующие OnStart/OnEnter/OnLeave становятся public override. Не добавлять фиктивные lifecycle-функции ради шаблона. Callbacks сохраняют точные типы и число аргументов; string &in / string & → string.
3. Статическое имя функции этого скрипта в аргументе → nameof(...); динамически собранное имя и пустая строка остаются как есть. Отсутствующую функцию не придумывать.
4. Глобальные переменные .hps → поля с исходным начальным значением, const → константы с тем же значением. Массивы сохраняют порядок, длину, индексы и повторы; resize/length переводить эквивалентно. Не превращать поля в local/global var API и наоборот.
5. Десятичные числа → float с f. Усечение float → int сделать явным. Целочисленное деление сохранить. Не переставлять границы RandFloat и не заменять его на RandInt ради удобства.
6. or/and/not → ||/&&/!. Не упрощать исходные условия и одинаковые ветки. Провал switch передать goto case с коротким английским пояснением. Перегрузки и возвращаемые значения переносить все; сверка уникальных имён сама по себе этого не доказывает.
7. Конкатенация float со строкой — через помощник с using System.Globalization:

   ```csharp
   /// <summary>AngelScript string + float (scriptstring addon: ostream, 6 significant digits).</summary>
   static string Str(float f) => f.ToString("G6", CultureInfo.InvariantCulture);
   ```

8. Сохранять ошибки оригинала. Если AngelScript молча прерывал вызов при выходе за границы массива, повторить выход в той же точке, с теми же предыдущими эффектами и порядком вычисления аргументов; не бросать C#-исключение и не продолжать после ошибки. Добавить короткое английское пояснение и исходную ссылку в журнал. Не окружать весь скрипт catch для сокрытия любых ошибок.
9. Все исходные NotPorted и пустые вызовы оставить. Нельзя обходить их ручным созданием сущностей, выполнением квестов или искусственной сменой состояния прямо в порте. Диагностические команды теста допустимы, но перечисляются отдельно от игрового поведения.
10. В журналах не копировать код игры: только ссылки файл:строка, имена и описание. Комментарии порта — исходные плюс необходимые короткие объяснения синтаксиса на английском.

## Последовательность работы с картой

### 1. Импорт

Сначала целиком прочитать скрипт, затем импортировать карту существующим методом. При уже существующей сцене переимпорт допустим только при согласованном доступе к Unity-проекту. До запуска проверить игнорирование импортируемой папки.

Обозначения команд: Unity.exe — `C:/Program Files/Unity/Hub/Editor/6000.6.2f1/Editor/Unity.exe`; Project — `Z:/Unity/RTXMnesia/UnityProj/UMnesiaRTX`; MapRel — `maps/main/ch02/<карта>.map`. Placeholders заменить реальными значениями. Все логи — по абсолютным путям внутри Project/Logs.

```text
Unity.exe -batchmode -nographics -quit -projectPath <Project> -executeMethod RTXMnesia.Importer.ImportMenu.ConvertLevelBatch -amnesiaMap <MapRel> -logFile <Project>/Logs/Import_<карта>.log
```

На Windows запускать через Start-Process с -WindowStyle Hidden -PassThru, дождаться WaitForExit() и проверить ExitCode. Следующий Unity запускать только после полного выхода предыдущего. При недоступном лицензировании sandbox использовать штатную эскалацию прав, не менять лицензию. Не выводить полные командные строки посторонних процессов: там могут быть токены.

Последний раздел карты в Logs/AmnesiaImport.log сохранить отдельным игнорируемым логом до следующего запуска. Требование: **0 ошибок и отсутствие исключений**, не только ExitCode=0. Виды и количества предупреждений выписать. При ошибке импорта остановить партию, импортёр не исправлять.

### 2. Порт и сверка

Создать класс по таблице этой части, перенести весь .hps, сверять после каждой правки .cs.

```powershell
powershell -ExecutionPolicy Bypass -File tools/Check-ScriptPort.ps1 -Chapter ch02 -Map <карта> -Port UnityProj/UMnesiaRTX/Assets/Scripts/Levels/Ch02/<Класс>.cs
```

Требование — 0 ошибок. Предупреждения об исходных отсутствующих callbacks или особых числах разобрать в журнале; не менять checker, не вставлять фиктивные строки/вызовы. Дополнительно вручную сверить сигнатуры, перегрузки, поля, все состояния switch/if, границы циклов и порядок эффектов. По возможности выполнить независимое сравнение токенов с нормализацией только разрешённого синтаксиса и проверку всех исходных комментариев.

### 3. Старт, события и состояние

```text
Unity.exe -batchmode -quit -projectPath <Project> -executeMethod RTXMnesia.EditorDev.PlayerSimulation.RunBatch -amnesiaMap <MapRel> -seed 1 -script "watch 30 2; shot start" -logFile <Project>/Logs/Sim_<карта>.log
```

GPU нужен: без -nographics. До запуска проследить стартовые таймеры и голосовые callbacks. Если за 30 секунд возможен автоматический ChangeMap/StartCredits, выбрать безопасную границу времени или диагностически снять конкретный таймер в сценарии, описав это в журнале; порт ради проверки не менять. Обычный старт и принудительное продолжение события — разные сценарии.

- Второй прогон: 5–10 основных обработчиков с точными аргументами, watch 10 2 после каждого. Для крупной карты — несколько отдельных прогонов. Точные команды составить после полного чтения исходника, по группам событий из таблицы этой части.
- Изолированно не вызывать функции/таймеры/голосовые окончания, прямо или косвенно выполняющие ChangeMap либо StartCredits. Эти пути проверять отдельным интеграционным прогоном после подготовки нужных сцен/систем. Не объявлять переход/финал проверенным по отсутствию исключений у заглушки.
- Предмет, разрушение объекта, появление ContainedItem и расходование одноразового триггера требуют исходной подготовки. Прямой call её не выполняет. Повторные регистрации после call сначала отличать от дефекта порта; снятие callback фиксировать в диагностическом сценарии.
- Для CheckPoint-карт проверить реальную смерть и нужные ветки счётчика. Дождаться возрождения: ориентир watch 20 2, затем health, позиция и состояние объектов; при ином актуальном времени ждать по состоянию. Для диагностики использовать летальный GivePlayerDamage, не SetPlayerHealth(0), у которого есть исходная особенность восстановления. Оригинальные SetPlayerHealth(0) в порте не исправлять.
- Разбирать Exception/PortError, takes N arguments, все [Script] ERROR, does not exist in, No function, отсутствие сущностей и повторные callbacks. HplLog.Error может попасть в отчёт как WARNING: «0 errors» не означает чистый скрипт.
- Отсутствие имени в .map ещё не доказывает ошибку оригинала: проверить динамические CreateEntity, .ent, ContainedItem, предыдущие события, .snt, wildcard и порядок подготовки теста. Если имя есть, проверить регистр, тип, активность и lookup. Дефект движка описывать отдельно, не чинить в карте.
- Выписать skipped, needs и отдельно пустые API без сообщения. Не выдавать активацию Enemy-сущности за работающий ИИ, а ручной Sticky callback — за физическое прикрепление.

### 4. Геометрия и проход

Просмотреть стартовый снимок и хотя бы один характерный вид, проверить короткий проход у старта, лестницу/мост при наличии. Использовать исходные PlayerStart через start <имя>, не неподтверждённые goto под полом. Указать, какая часть маршрута проверена.


Сохранить Logs/HplMeshAudit.txt отдельным Audit_<карта>.txt. Различать геометрию моделей, трансформы сцены, матрицы префабов и регрессию выбора ресурсов. Не объявлять общий PASS при ExitCode=1.

Из опыта главы 1: версия аудитора на дату плана проверяет MeshFilter и может не учитывать SkinnedMeshRenderer; поиск по имени может брать первый из одинаково названных объектов. Разбирать по типам рендереров, исходным ID, FileIndex и сериализованным путям. Это гипотезы для конкретной проверки, не разрешение игнорировать любые failures. Аудитор/импортёр ради зелёного результата не править.
